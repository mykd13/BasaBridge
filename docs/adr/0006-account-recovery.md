# 0006 Account recovery for learners without email

Status: proposed. Date: 2026-10-18. Issue: BB-62.

## Problem

A student may sign up with a username and no email (ADR 0005). If that student has no linked parent and forgets the password, there is no way back in. Children forget passwords often, and losing an account loses their levels and progress.

## Decisions

1. **A recovery code at sign-up.** A student who signs up without an email is shown a recovery code once. The screen uses large type and has a copy button and a print button. The learner ticks a box to say they saved it before going on.
2. **Code format.** 16 characters from `23456789ABCDEFGHJKMNPQRSTWXYZ`, shown as four groups of four (`ABCD-EFGH-JKMN-PQRS`). The alphabet leaves out 0, O, 1, I, L, U and V, which children mix up. That is about 78 bits, too many to guess. Typed codes ignore case, spaces and dashes.
3. **Stored hashed, never retrievable.** Only a salted scrypt hash is kept (`apps/web/src/server/auth/recovery-code.ts`). No column, log or screen holds the plain code after the one screen that shows it. A `recovery_codes` table holds `user_id`, `code_hash`, `created_at`, `acknowledged_at` and `used_at`. Only the newest unused code works.
4. **Reset with username and code.** The learner types the username, the code and a new password. In one transaction the server checks the code, sets the password, marks the code used, makes a new code and signs out every session. The new code is shown once, on the same screen as decision 1. A wrong code and an unknown username give the same answer.
5. **Rate limited.** Recovery tries use the BB-7 lockout counter with their own key (`recovery:user:<id>`), so they cannot lock or unlock sign-in. A per-address limit sits on top, using whatever BB-39 settles on. The numbers live in `authConfig`.
6. **Printing without a second route.** The print button prints the same screen with a print stylesheet. A separate printable route would need the code again, and the code cannot be read back.
7. **Other ways back in.** A learner with an email keeps the BB-7 email reset. A linked parent can start a reset only when the learner has turned on a new `shares_recovery` flag on `parent_links`, which is off by default. The reset link goes to the parent's email. The learner sets the new password. The parent never sees the password or the recovery code.
8. **A new code from My account.** A signed-in learner can make a new code after typing the current password. The old code stops working at once.
9. **Spoken help, never the code.** Every step has fixed instruction sentences with audio (BB-57, ADR 0004). The recovery code and the username are never sent to a text-to-speech provider (AGENTS rule 2). The code is read on screen only.

## Consequences

- `packages/db` gains `recovery_codes`, and `parent_links` gains `shares_recovery`. Both are locked areas (Rhett).
- The authorization layer (BB-10) gains a `recovery` check for parents: active link and `shares_recovery` on.
- `signUpStudent` returns the code once in its result. It is never written to a log.
- New screens are needed on the design canvas: the code panel, the recover form, the success state with a new code, the My account action and the share toggle (Sean).

## Trade-offs

- **A lost code and no email means no way back.** We accept this. The sign-up screen says so kindly and suggests printing the code or giving it to a trusted adult.
- **A printed code can be found by someone else.** Anyone with the username and the code can reset the password. The code is single-use, using it signs out every session, and the learner can make a new one at any time.
- **scrypt costs some server time.** About tens of milliseconds per check. The rate limit keeps that small.
